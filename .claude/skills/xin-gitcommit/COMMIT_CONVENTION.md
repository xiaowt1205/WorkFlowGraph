# Git Commit Message — WorkFlowGraph 專案規範

> 本規範由公司 Unity 專案的 commit 規範改寫而來，保留格式與 Type 分類的骨架，
> 移除 Unity 專屬條款（場景異動、Localization / GameStreet、`editor` 工具類型），
> 改為對應本專案的結構：零依賴 Node 伺服器 ＋ 單檔前端 ＋ 文件。

## 標準格式

```
<Type>: <Subject>
(空一行)
<Body>
(空一行)
<Footer>
```

- `<Type>` 與 `<Subject>` 為**必填**。
- `<Body>` 與 `<Footer>` 為選填，但有填時**與標題之間的空行不可省略**。
- 若這次改動對應 GitLab issue，`<Footer>` 為**必填**。

---

## Type 類型（只能選一個）

| Type       | 說明                                                                       | 需要驗證 |
|------------|----------------------------------------------------------------------------|----------|
| `feat`     | 功能上的變動，包含新增、修改、刪除（新節點型別、畫布操作、API 端點）        | ○ 需要   |
| `fix`      | 修正錯誤                                                                   | ○ 需要   |
| `refactor` | 功能不變的情況下調整或優化程式碼（如抽出共用函式、重構選取模型）            | △ 補充說明 |
| `perf`     | 以優化效能為重點的修改（如減少整頁重繪、降低 renderAll 次數）               | △ 補充說明 |
| `chore`    | 不改功能也不修 bug 的雜項（`.gitignore`、開發腳本 `scripts/ctl.js`、目錄調整） | ✕ 不須   |
| `style`    | 純格式調整（縮排、註解、空白），不影響行為                                 | ✕ 不須   |
| `docs`     | 文件更新（README、NODES、`principles/`、CLAUDE、CHANGELOG）                | ✕ 不須   |
| `test`     | 新增、修改、移除測試                                                       | ✕ 不須   |
| `build`    | 版本號、`package.json` 設定、發佈相關                                      | ✕ 不須   |
| `merge`    | 合併分支、修正衝突                                                         | ✕ 不須   |

### Type 選擇規則

- **只能選一個**，不可填複數 Type。
- 同時包含 `fix` 與 `feat` 時，因有修正原本錯誤的功能，**優先使用 `fix`**。
- **改動使用者操作方式（快捷鍵、滑鼠行為、預設值）一律算 `feat` 或 `fix`，不是 `style` 也不是 `docs`**，
  即使程式碼改動很小——因為使用者感受得到。
- 只有在**行為完全不變**時才可用 `refactor` / `style`。

---

## Subject 標題規則

- 言簡意賅描述此 commit 的改動。
- **不超過 50 字**，中英文皆**不用句號結尾**。
- 盡量以**祈使句**書寫，優先使用繁體中文（與既有 commit 風格一致）。
- 涉及特定區塊時，建議以「區塊，動作」開頭，讓 log 一眼可掃：
  - `畫布，…` / `節點，…` / `伺服器，…` / `文件，…`
- **不應只寫 issue 編號**，需描述實際改動內容。

---

## Body 本文規則（選填）

- 標題不足以完整描述改動時再填。
- 每行不超過 72 字；多項內容用 `-` 或數字列點，相關內容放同一行。
- 描述**行為與影響**，不要逐行複述程式碼改了什麼。
- **操作方式或預設行為有變更時，必須在 Body 寫出「原本是什麼 → 改成什麼」**，
  例如：`- 平移改為中鍵或 Space+左鍵（原本是左鍵拖曳空白處）`。
- 若有相容性影響（舊工作流 JSON 的匯入遷移），必須在此註明。

---

## Footer 頁尾規則（有 issue 編號時必填）

- 格式固定：`issue <編號>`，編號即 GitLab issue 號碼。
- 多個 issue 分多行撰寫。
- **編號只能來自使用者明確提供**，禁止自行猜測或從 diff 推導。

```
issue 12
issue 15
```

## 完整範例

### 範例 1：有本文，操作方式變更

```
feat: 畫布，改為中鍵平移並支援框選與右鍵節點清單

- 平移改為中鍵拖曳或 Space+左鍵（原本是左鍵拖曳空白處）
- 左鍵拖曳空白處改為框選，Shift 為加選
- 空白處右鍵開節點清單，可搜尋、↑↓ 選、Enter 新增
- 多選支援整組拖曳、Del 刪除、Ctrl+D 複製（含節點間連線）
```

### 範例 2：有本文與頁尾

```
fix: 節點，修正輸出檔案節點副檔名判斷錯誤

1. 修正檔名已帶副檔名時仍被格式參數覆寫的問題
2. 補上未指定資料夾時落到 outputs/ 的路徑處理

issue 12
```

### 範例 3：只有標題

```
docs: 節點總覽從 README 拆到 NODES.md
```

### 範例 4：雜項

```
chore: 忽略 .claude/ 與執行期產物
```

## 撰寫流程

1. **判斷 Type**：依改動內容選唯一 Type；同時有 fix 與 feat 時優先 `fix`；
   使用者感受得到的行為變更不可歸到 `style` / `refactor`。
2. **寫 Subject**：50 字內、祈使句、不加句號、不只寫 issue 編號。
3. **判斷是否需要 Body**：標題能完整說明就不寫；有多項改動、操作方式變更、
   相容性影響時必須補上。
4. **判斷是否需要 Footer**：有 issue 編號就必填，每個一行。
5. **檢查空行**：有 Body 或 Footer 時，確認與 Subject 之間有空行。
