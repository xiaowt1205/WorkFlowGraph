# WorkFlowGraph 節點設計原則

本文件是新增或修改節點的**強制規範**。任何節點需求都必須先對照本文件，違反原則的設計必須先修改設計，而不是修改原則。原則本身要改，需明確提出並記錄理由。

版本：1.0（2026-08-24）

---

## 一、核心原則

### 1. 節點是純函數
節點 = `(inputs, params) → outputs`。同樣的輸入與參數，必須得到同性質的輸出。

- 節點**不知道圖的存在**：不讀取其他節點、不觸碰 `state.nodes` / `state.edges`，只透過 `ctx` 拿東西。
- 節點**沒有記憶**：每次執行從零開始，不得在節點間隱式共享狀態。跨節點的資訊傳遞只有一條路——連線。
- 需要上下文就顯式接線（例如把原始輸入再接一條線給下游），不做隱式傳遞。

### 2. 能力邊界用機制保證，不靠提示詞
節點能做什麼、不能做什麼，由**程式碼與呼叫參數**決定，不由 system prompt 決定。

- LLM 節點是純文字進出：後端以 `--tools ""` 把 claude 的內建工具**整組關掉**（白名單為空），
  再以 `--strict-mcp-config` ＋空的 `--mcp-config` 把 claude.ai 連接器與外掛的 MCP 工具也拔掉，
  模型的世界裡不存在寫檔、執行指令、ToolSearch 這些選項。`--disallowedTools` 黑名單只是第二道保險。
- 需要特定工具的節點（如網路查詢）以白名單開放（`--tools WebSearch,WebFetch` ＋ `--allowedTools`），其餘照樣不存在。
- **白名單，不是黑名單。** Claude Code 每版都會新增工具（ToolSearch、Skill、Artifact、Cron…），
  黑名單一定會過時；2026-10-22 就是這樣破的：純文字節點透過 ToolSearch 摸得到 Google Drive 分享／刪檔。
  同一天實測：黑名單 36.6k 輸入 token、把 ToolSearch 加進黑名單反而 73.5k、白名單＋空 MCP 設定 3.2k。
- 提示詞（如「輸出限制」的守則注入）只能作為**品質優化**，之後必須跟一道**強制後處理**（如抽取程式碼區塊）做硬保證。軟約束後面沒有硬保險的設計不予接受。

### 3. 單一職責
一個節點只做一件事。

- 產生內容的節點不做 IO；讀檔是「外部檔案連結」、寫檔是「輸出檔案」的專屬職責。
- 檔案落點由 workflow 明確控制（節點參數），永遠不交給模型自由發揮。
- 想要複合行為，用多個節點接線組合，不做瑞士刀節點。

### 4. 不允許無聲行為（No Silent Behavior）
節點做了任何使用者可能意想不到的事，**必須**用 `ctx.log()` 講出來：

- 丟棄資料（例：合併取第一個時忽略其餘輸入 → 必須列出忽略了誰）。
- 清洗/轉換輸出（例：剝除程式碼圍欄、抽取 JSON → 必須記一筆）。
- fallback 行為（例：找不到區塊原樣輸出、超長截斷）。
- 靜默截斷、靜默覆蓋、靜默跳過，一律禁止。

### 5. 內建節點只放通用能力，特定功能做成模組發布

`NodeTypes` 註冊表是**通用運算單元的集合，不是功能清單**。一個能力要成為內建節點型別，
必須**與領域無關**：換一個題目、換一個專案、換一個部門，還是會用到它。

特定的業務流程**不進註冊表**——用既有的通用節點在 FlowMap 裡組出來，介面用
📥 節點輸入／📤 節點輸出 標記清楚，**存成 FlowMap 當模組發布**給別的 FlowMap 引用。

**開發順序是固定的：先 FlowMap，後節點。**收到「要一個新節點」的需求時，先把它當成
「要一個新模組」來做——用現有節點組出 FlowMap、標好 📥／📤 介面、發布——**做不出來**才回到
這一節評估要不要新增型別。「新增節點型別」是最後手段，不是第一步。

要新增節點型別前，這三題全部要 yes：

| 判準 | 沒過就做成模組 |
|---|---|
| **通用嗎？** 節點名稱或職責說明裡，出現了特定專案／部門／業務的名詞嗎？描述它需要提到某個流程嗎？ | 「把 A repo 的 commit 區間搬到 B repo 並 stage」是**流程**；「在指定 repo 做一次 git 查詢」是**能力** |
| **組不出來嗎？** 用現有節點（程式碼／Shell／HTTP／檔案讀寫／條件分支）＋接線做得出來嗎？ | 做得出來就做成模組。**「這樣比較方便」不是理由**——少接兩條線，不值得多一個全域概念 |
| **是原語嗎？** 它是一個動作，還是一串決策？ | 含「先看有沒有異動、有的話才搬」這種**政策**的，政策要留在圖上（條件分支），不要縫進節點 |

為什麼要這麼嚴——**內建節點的成本是永久且全域的**：

- 它會出現在節點庫、右鍵清單、`NODES.md`、`README.md`，每個使用者都得多認識一個東西；
- 一旦有人的圖用了它，就**再也拔不掉**（見八、相容性義務），連改埠名都要寫遷移；
- 型別名進了存檔格式，等於一份長期 API。

模組沒有這些成本：它只是一張 FlowMap。改實作、改名、廢棄，只影響引用它的人；
而且引用是即時的（執行時載入來源最後儲存的版本），改一處全部生效。

**唯一的例外**：那個能力**非有後端不可**，而用 ❯ Shell 指令 做等於把「在本機執行任意指令」
開給整張圖。這種「把一個本機能力安全地包成受限原語」可以是內建，但**原語要切在
「通用動作」那一層，不要切在「業務流程」那一層**，而且必須在十、既往決策記錄寫下理由。

## 二、節點型別定義規範

新節點一律加進 `NodeTypes` 註冊表，形狀如下：

```js
mynode: {
  title: '顯示名稱',          // 繁體中文，2~6 字
  color: 'var(--c-mynode)',   // 在 :root 新增專屬色票，不重用他人顏色
  icon: '◇',                  // 單一字元/emoji
  inputs:  [{ name: 'in',  label: '說明', multi?, requireAll? }],
  outputs: [{ name: 'out', label: '說明' }],
  params:  [{ key, label, kind, def, ... }],
  summary: n => '卡片上的一行摘要',   // 摘要必須「準確」，寧可空白不可誤導
  async run(ctx) { return { out: value }; }
}
```

規則：

- **埠用具名**（`prompt`、`content`、`ref`），不用無意義的編號；例外是通用聚合埠可叫 `in`。
- **params 只用既有 kind**：`text` / `textarea` / `number` / `select` / `file` / `folder`。需要新 kind 先擴充檢查器渲染器，不得在節點內自造 UI。
- **label 要寫清楚限制與慣例**（支援哪些格式、留空的行為），使用者不看文件也能用。
- **summary 是承諾**：卡片摘要必須反映節點當前參數的實際行為。曾因摘要誤導使用者而移除過摘要——寧缺勿誤。
- run 的回傳是 `{埠名: 值}`；只 emit 有值的埠（條件分支語意依賴這點）。
- 拋出 Error 的訊息用繁中、講人話、給下一步（「未指定檔案路徑（在右側檢查器填入，或接線到 path 埠）」）。
- **動態埠的唯一例外**：`subflow`（FlowMap 模組）的埠由來源 FlowMap 的輸入／輸出節點
  決定，存於節點的 `params._ports`，由 `typeOf()` 注入。因此**取節點的埠定義一律走
  `typeOf(n)`，不得直接讀 `NodeTypes[n.type].inputs`**；引擎、渲染、接線都依賴這條。
  新節點若無充分理由，不得再引入動態埠。

## 三、埠與連線語意

- 輸入埠預設**單線**：新連線自動取代舊連線。
- `multi: true`：同一埠可接多條線，值依**接線順序**收集成陣列，並附 `ctx.sources`（來源節點名稱＋值），供 `@節點名稱` 引用等機制使用。
- `requireAll: true`（配 multi）：任一條連線死掉（上游被跳過）→ 本節點跳過。用於「所有輸入都是必要材料」的節點（Prompt 模板）。
- 不設 requireAll 的 multi 埠：至少一條活著就執行。用於會合點（合併）。
- 輸出埠天然可扇出（一個輸出接多條線），不需宣告。
- **選擇器與彙整器要分明**：會丟資料的模式（取第一個）不得是預設；預設必須是不丟資料的行為（全部串接），且丟資料時必須 log。

## 四、執行語意（引擎契約，節點不得假設以外的行為）

- 拓撲排序執行，有循環拒跑。
- 節點執行時，所有上游必然已「完成／出錯／跳過」三者之一。
- 條件類節點一次只 emit 一個輸出埠；未 emit 的埠下游整條**傳染式跳過**。
- **被跳過的節點 `run()` 不會被呼叫**——不是執行後丟棄，是根本不執行。它沒有輸出值（不是空字串、不是 null，是不存在）。
- **「沒有資料通過」有兩種死因，必須分開報**：① 上游是條件分支沒選中而跳過 ② 上游節點執行失敗。
  兩者的處理一樣（下游整條不執行），但**說法不能一樣**——把失敗說成「分支未選中」會讓使用者
  往錯的方向找問題。引擎用 `skipped`（資料流用）與 `failed`（死因用）兩個集合，
  失敗要沿鏈往下游傳，節點卡片／檢查器／連線提示三處都要照死因換文字。
- 中斷（AbortController）：節點內所有 `fetch` 必須掛 `ctx.signal`，確保按「⏹ 中斷」時請求立即取消。
- **會話表（`ctx.sessions`）是引擎提供的執行期資源**：會話名 → `{ sessionId, bindKey }`，
  由 `runGraph` 每次執行新建、跑完即棄，**不序列化、不跨執行**；經 `runSubgraph` 原樣傳入
  模組內部（跨模組共用同一張表）。它不違反「節點沒有記憶」：共用發生在**作者於參數明確
  宣告相同會話名**之時（顯式，圖上可審計），預設（留空）仍是完全隔離；且所有會話行為
  （首次／延續／綁定不符改開新會話）都必須 `ctx.log`。節點不得把會話表當成傳資料的旁路
  ——資料傳遞仍然只有連線一條路，會話只承載「模型上下文的重用」。

## 五、狀態回饋（UI 義務）

節點的五種狀態必須在畫布上可辨識：`idle` / `running`（脈動）/ `success`（綠）/ `error`(紅) / `skipped`（虛線半透明＋「⊘ 未執行—無輸出值」說明框）。

- 有資料通過的線顯示綠色流動；沒資料通過的線顯示 ⊘ 標記與 hover 說明。
- 「沒有執行」「沒有輸出」這類否定事實也要明示，不能讓使用者猜。
- 執行結果在節點卡片與檢查器都要能看到；錯誤訊息完整顯示於檢查器。
- **暫態狀態不進圖。** 「上一次執行的畫面狀態」不是圖的內容，混進去就會被當成使用者的改動
  （工具列亮 ●、返回總覽跳對話框），還會被存進檔案，下次開啟畫出從未發生過的執行結果。分兩種：
  - **連線上的暫態**（`_flow` / `_dead` / `_deadErr`）用 `_` 開頭，序列化時由 `graphData()`
    濾掉、讀入時由 `loadedGraph()` 洗掉。
  - **節點上的暫態放在圖外面**（例如「來源 FlowMap 不存在」用模組層級的 `missingModules`
    集合）。**不要學連線用 `_` 前綴**：節點的 `params._label` / `_ports` / `_wsName` 是
    要存檔的持久欄位，`_` 在這裡不代表暫態，濾不得。

## 六、使用者輸入慣例

- 跟隨 OS 慣例：檔名副檔名優先於類型欄位、用系統原生檔案/資料夾選擇對話框（後端 `/api/pick`）。
- 欄位**即打即存**（input 事件即回寫狀態），不得依賴失焦才儲存。
- 路徑類參數一律提供「📂 瀏覽」按鈕（kind: `file` / `folder`）。

## 七、後端呼叫規範（節點需要新 API 時）

- 新端點加在 `server.js`，維持**零外部依賴**（只用 Node 內建模組）。
- 呼叫本地 Claude 一律走 `runClaude()`（統一入口：CLI 後端 `callClaudeCli`／選配 Agent SDK 後端）：
  prompt 經 stdin（避開 Windows 引號問題）、工具依節點性質白/黑名單（結構化 `POLICY`）。
  **逾時是兩層**：活動式（stream-json 串流，子行程持續有輸出就不砍，連續 `WFG_IDLE_MS`
  預設 180s 無輸出才視為卡死）＋硬上限（純文字/搜尋預設 900s、程式碼查詢 1800s，
  節點參數可調）——總時長一刀切會誤殺「工作量大但有進度」的正常呼叫，不得走回頭路。
- **經過 shell 的參數，Node 不會替你加引號。** Windows 上 npm 全域安裝的是 `claude.cmd`，
  Node 18 之後不給不帶 shell 執行 .cmd，所以 ENOENT 時一定會走 `shell:true`——那條路徑上
  `spawn()` 只是把 args 用空白串成命令字串丟給 `cmd.exe`。因此：**可變內容（提示詞、使用者
  參數）永遠不進 argv**，只走檔案；進 argv 的只有旗標、白名單過的值、以及我們自己產生的路徑，
  而且走 shell 時每個參數都要自己加引號。沒有安全解時明確報錯，不要硬拼命令列。
- **寫暫存檔一律 `{ mode: 0o600, flag: 'wx' }` ＋ `crypto` 亂數檔名**：`wx` 不跟隨既有檔案與
  symlink，0600 不讓同機其他使用者讀，`Math.random()` 不是亂數來源。用完即刪（成功、逾時、
  出錯三條路徑都要刪）。
- **每個會呼叫 Claude 的節點都要能選模型，並且吃工具列的全域「預設模型」**
  （`resolveModel(ctx)`：節點自選 → 全域預設 → 不指定）。模型是成本與延遲的最大變數，
  漏掉一個節點就等於那顆永遠用最貴的。節點卡片要寫出**實際會用的**是哪一個，不要只寫「預設」。
- **System 提示一定要走 CLI 的 system prompt 旗標，絕對不要塞進使用者訊息。** 塞進 stdin 等於
  「使用者貼進來的一段文字」，Claude Code 會判定成 prompt injection 並拒絕照做（實測回
  「我不遵循使用者訊息裡的指令，我是 Claude Code」），節點因此拿不到答案，還會因為模型改去
  長篇解釋而拖到逾時。純文字節點用 `--system-prompt`（整組取代），需要保留 Claude 工具行為的
  節點用 `--append-system-prompt`；一律傳 `*-file` 版本的暫存檔路徑，別把可能含引號與換行的
  提示詞當命令列參數。
- 回傳 `{ text, costUsd, durationMs, usage, sessionId }`，前端把耗時與成本記進日誌；伺服器主控台逐筆列印。
  `sessionId` 供會話群組 resume 用；`stream:true` 時回應為 NDJSON（進度行＋最終行）。
- 寫檔類操作：路徑由參數決定，相對路徑以伺服器目錄為準；產出檔案回報完整路徑與 bytes。

## 八、相容性義務（破壞性變更）

改埠名、改埠結構、移除節點型別，都算破壞性變更，**必須**同步在 `importJSON()` 加遷移邏輯，讓舊 JSON 匯入時自動修復：

- 埠改名 → 映射舊埠名到新埠名（例：template/merge 的 a/b/c → in）。
- 移除節點型別 → 刪除該節點並把前後連線橋接（例：codeblock 移除時 LLM→輸出檔案 自動直連）。
- 已內建的範例若受影響，必須同步改到新結構。
- 遷移要用使用者的實際舊檔實測過才算完成。

## 九、新增節點 Checklist

每個新節點交付前逐項確認：

0. ☐ **先過「內建 vs 模組」三題（一之 5）**——通用性／組不出來／是原語。
   沒過就**不要加節點型別**，改用現有節點組成 FlowMap 發布為模組。這題沒過，底下不用看。
1. ☐ 符合純函數原則（無隱藏狀態、不碰全域圖）
2. ☐ 能力邊界有機制保證（不是只靠提示詞）
3. ☐ 單一職責，不與既有節點重疊（先問：現有節點加參數能不能解決？）
4. ☐ 所有意外行為都有 `ctx.log`
5. ☐ 專屬色票、icon、準確的 summary
6. ☐ 錯誤訊息繁中、可行動
7. ☐ 所有 fetch 掛 `ctx.signal`（可中斷）
8. ☐ 模擬模式有合理行為（不呼叫 Claude 的節點可維持真實行為）
9. ☐ 若動到既有埠/型別：importJSON 遷移 + 範例更新
10. ☐ Playwright 實測：正常路徑、錯誤路徑、（有分支時）跳過傳播
11. ☐ README 節點清單同步更新

## 十、既往決策記錄（為什麼是這樣）

- **合併預設「全部串接」**：原「取第一個有值」曾無聲丟棄使用者資料（2026-08-24）。選擇器行為保留為選項且必須 log。
- **LLM 節點拔除全部工具**：模型看得到 Write 工具就會嘗試寫檔、被權限擋、再花 token 解釋。工具不存在，行為就不存在。提示詞勸說不可靠（同日驗證）。
- **移除「取程式碼區塊」節點**：其職責由 LLM 節點內建「輸出限制」（守則注入＋強制後處理）取代——保險應該長在產生內容的節點上，而不是要求使用者記得多接一個節點。
- **模板 requireAll、合併 any**：讓條件分支的閘門效果能穿過模板向下傳播，同時讓會合點只要一邊活著就能接。
- **摘要寧缺勿誤**：合併節點曾因摘要文字與實際行為不符而誤導使用者。
- **Shell 指令節點的閘門設計**（2026-08-26）：一個能在本機執行任意指令的節點，配上「工作流可
  匯出／匯入／分享」，就是一條把別人的圖變成本機執行的路。決議是**三道機制**而不是提醒：
  模擬模式不呼叫後端、工具列總開關（預設關且**不持久化**）、逐段指令首次確認（核准不進存檔）。
  同時**不開「指令」輸入埠**——上游的值只走 stdin 與 `WFG_IN`，命令列的形狀永遠由圖的作者決定，
  這樣「LLM 產生的文字」永遠只是資料，不會變成指令。伺服器也一併改為只聽 loopback。
  將來若要加「上游決定指令」的能力，必須是預設關閉的獨立參數＋逐次確認，不得動到上面任何一道。
- **FlowMap（時稱 Workspace）模組的介面改用專屬的「節點輸入／節點輸出」明確標記**（2026-08-25，
  同日推翻「一般輸入／輸出節點自動對映」的初版設計，依使用者要求）：模組的埠必須是
  來源作者**明確標記**的——自動對映會把來源所有的輸入／輸出節點都暴露成埠，
  來源加一顆普通輸入節點做內部測試，引用端的介面就默默多一個埠。改為：有「節點輸入」
  才有輸入埠、有「節點輸出」才有輸出埠，一般輸入／輸出節點與埠無關。
  節點輸入帶預設值（單獨執行或埠未接線時使用），節點輸出單獨執行時同「輸出」，
  來源因此仍可獨立測試。埠名採內部節點 id，改顯示名稱不會斷線。引用是即時的
  （執行時載入來源最後儲存版本），循環引用以 visited 集合在執行時硬性擋下
  （機制保證，不靠清單過濾）；清單過濾只是第一道 UX 防線。
  引擎核心抽出 `topoOrder` / `collectPortInputs` 供頂層與子圖共用，兩邊語意必須一致。
- **會話群組做成顯式資源，粒度不綁 FlowMap**（2026-08-26，成本優化討論的決議）：
  「一個 FlowMap 共用一個 session」被否決，理由有三——① 它把需要隔離的節點
  （只看 skill 作答、對碼查證、拷問官）默默打通，機制保證的隔離退化成提示詞假裝；
  ② 尾端節點揹著整段無關歷史付快取讀取費、還被前文干擾；③ 單一 session 天生序列，
  堵死將來的同層並行。改為：AI 節點以「會話名」參數明確宣告共用（同名同會話、留空即
  隔離），會話跟著「同一批材料／同一次讀碼」走而非跟著圖走。逾時同時從總時長改為
  活動式（stream-json 有輸出就不砍）＋硬上限兩層——總時長逾時會誤殺「工作量大但有
  進度」的正常呼叫。後端抽出 runClaude 統一入口，CLI 與 Agent SDK（WFG_BACKEND=sdk，
  選配）共用同一契約。
- **模組共享改為「同 Project 自動互通＋公開跨 Project」**（2026-08-27，依使用者要求，
  取代「發布為節點」開關）：FlowMap（原名 Workspace，同日全面更名）以 Project 分類；
  同一個 Project（或同為未分類）的 FlowMap 直接互相可當節點引用，不需任何設定；
  跨 Project 引用需來源在總覽勾「🌐 公開」。能見度只決定能不能**新增**引用
  （節點庫／右鍵清單看不看得到），既有的模組節點照常執行——與先前「取消發布不斷既有引用」
  的語意一致。舊資料的 `published:true` 讀取時遷移為公開、`workspaces/` 啟動時遷移為
  `flowmaps/`、模組節點的 `wsId`/`_wsName` 載入時遷移為 `fmId`/`_fmName`。

- **版控搬移做成三顆節點，閘門只擋刪除**（2026-08-27，依使用者要求）——**⚠ 已於同日推翻，三顆節點與端點全部移除，見下一則「內建節點只放通用能力」。以下保留當時的推理，因為閘門密度的取捨在模組版仍然適用。**：桌面版「版控搬移工具」
  的能力移植進來時，先否決了「一顆全包」——列 commit、預覽區間、實際搬移是三件事，
  瑞士刀節點會讓「唯讀盤點」與「寫入目標 repo」共用同一顆，摘要與狀態就講不清楚它這次做了什麼。
  改為 📜 Commit 清單（唯讀）／🧾 區間預覽（唯讀）／🔀 版控搬移（寫入）三顆，代價是預覽與搬移
  各跑一次 `git diff`（毫秒級，可接受），換到的是「唯讀的兩顆在模擬模式維持真實行為、
  寫入的那顆在模擬模式完全不碰後端」這條乾淨的界線。
  閘門的密度也是明確取捨：**只有刪除要確認，覆寫不問**。理由是被 git 追蹤的覆寫拿得回來，
  刪除（含改名的舊檔）才是真正不可逆的那一半，把完整清單攤開才有意義；同時**不加**第二個
  「允許搬移」總開關——Shell 節點需要它是因為指令內容可以隨匯入的圖任意變形，而搬移節點的
  形狀固定（來源／目標／區間），危害面收斂在使用者自己選的兩個資料夾裡。
  這個取捨的代價要說清楚：**目標 repo 裡還沒 commit 的變更會被覆寫掉**，文件與節點註解都寫明。
  另外沿用 Shell 節點的教訓：搬移的三個路徑／區間**接線優先於參數**，但生效的是哪一個一律
  `ctx.log`，且卡片摘要要標出「接線提供」——否則接了線的節點會顯示「未指定」，那是誤導。

- **MCP 接法做成兩顆節點、邊界全靠旗標**（2026-10-22）：🔌 MCP 工具 是確定性的「呼叫某個工具」
  原語（只做 Streamable HTTP：initialize／`Mcp-Session-Id`／SSE 這些 HTTP 請求節點組不出來，
  stdio 等於 spawn 指令、刻意不做）；🤖 MCP 代理 是「把這幾台 MCP 的工具交給 Claude」的代理原語，
  任何傳輸都能接。後者的能力邊界是 `--tools ""` ＋ `--strict-mcp-config <節點專屬設定檔>` ＋
  `--allowedTools mcp__<名稱>`，模型看得到的工具恰好是節點填的那幾台（實測自述一致）。
  stdio 型設定會在本機啟動指令，而圖可分享，所以閘門完整照搬 Shell 節點三道，一道不少；
  HTTP 型不設閘門。同日也把所有 AI 節點的工具政策從黑名單改成白名單（見一之 2）——
  起因正是在測這顆節點時發現純文字 LLM 節點透過 ToolSearch 摸得到 claude.ai 連接器。
- **內建節點只放通用能力，特定功能做成模組**（2026-08-27，依使用者要求立為原則，見一之 5）：
  起因是同日一度為「版控搬移（搬館）」加了三顆節點——📜 Commit 清單、🧾 區間預覽、🔀 版控搬移
  ——以及三個 `/api/git/*` 端點。它們解決了真的問題，但把**特定業務流程**寫進了全域註冊表。
  照三題判準逐一對照，結論是**三顆都不該存在**，已全部移除、伺服器與前端回到原狀：
  - 第一題（通用嗎）：🔀 版控搬移 的名字就是業務流程，明顯不過；
    📜 Commit 清單、🧾 區間預覽 看起來像通用 git 原語，其實它們的埠與輸出格式
    （淨異動、要刪清單、內文彙整）都是為了搬館這條流程而切的。
  - 第二題（用現有節點組不出來嗎）：**這才是關鍵，而它們過不了。** 當初的判斷是
    「程式碼節點是沙箱、沒有檔案系統，所以只能加節點」——漏掉了 ❯ Shell 指令 節點本身
    就是「安全地在本機執行外部程式」這個通用能力，而它已經內建、已經有三道閘門。
    用 Shell 節點跑 git 取檔完全做得到（實作最後用的是 `git checkout-index` ＋
    `GIT_INDEX_FILE` 指到暫存索引；第一版的 `git archive` ＋ `tar -xf` 因為 Windows 的
    bsdtar 用系統碼頁解檔名、中文會爛而放棄）。
  - 第三題（是原語嗎）：🔀 版控搬移 內含「複製 ＋ 刪除 ＋ stage」與刪除確認，是一串政策。
  改法與代價（都已落地在「搬館工具」Project 的四張 FlowMap）：政策移回圖上——
  ⑂ 條件分支 擋「沒異動不搬」、⌨ 輸入＋⑂ 條件分支 擋「同步刪除」（預設否）、
  ✍ Prompt 模板 的 requireAll 當材料聚合器兼閘門（順序與前置條件）、
  ⇥ 合併 收三個模組的 stderr（否則失敗只會顯示「分支未選中」，看不出死因）。
  換來的代價要說清楚：① 刪除的確認從「節點內彈窗攤開檔案清單」退回「預覽階段先看清單、
  人決定要不要把開關轉成是」＋Shell 節點自己的逐段指令確認；② 每次重新整理都要重開
  工具列的「允許 Shell」；③ 取檔改依賴本機的 `git`（本來就要有）——一度想用的 `tar` 路線已因中文檔名問題放棄。
  這條原則的實質意義是**預設值反過來**：以前是「需要新能力 → 加節點」，
  現在是「需要新能力 → 先問現有節點（尤其 Shell／程式碼／HTTP）能不能組出來，
  組得出來就做成模組發布」。
